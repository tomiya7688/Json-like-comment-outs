# クラス説明書生成ツール 仕様

Status: **Design Draft**

> この日本語版を正本 (canonical) とします。  
> 現時点では設計段階であり、実装は行いません。

## 1. 目的

ソースコードに書かれたコメントを解析し、**クラスごとの Markdown 説明書**を生成します。

主な入力情報:

- クラス宣言前の JSON-like Comment Out
- 関数 / メソッド宣言前の JSON-like Comment Out
- 関数 / メソッド内部の通常コメント

このツールはコードそのものの意味を評価するのではなく、**コメントに書かれている情報を読みやすい説明書・仕様書へ再構成する**ことを目的とします。

### Comment-driven documentation

このツールの中心的な考え方は、

> **コメントをきちんと書けば、そのコメントから仕様書が作れる**

ことです。

コードを先に実装する場合は、宣言前コメントと実装内部コメントを整えることで、そのまま説明書を生成できます。

逆に仕様を先に作る場合は、

1. クラス / 関数の宣言を用意する
2. JSON-like Comment Out と通常コメントを先に書く
3. このツールで Markdown 仕様書を生成する
4. コメントを仕様として実装する

という使い方も想定します。

つまり、コメントは単なる実装後の補足ではなく、**コードの直前に置ける仕様記述**として利用できます。

## 2. 非検証ツール

このツールは以下を検証しません。

- コメントと実装が一致しているか
- 関数の処理が正しいか
- クラスの責務が適切か
- 引数や戻り値の説明が実際の型・挙動と一致しているか
- 関数内部コメントが実際の処理内容を正しく説明しているか

例えばコメントに、

```text
責務: ユーザーを取得する
```

と書かれていれば、実装がユーザーを取得していなくても、その内容を説明書へ出力します。

**Source of truth for this tool = comments**

とします。

## 3. 基本出力

クラスごとに Markdown を生成します。

例:

```markdown
# UserService

## 責務

ユーザー情報の取得・更新を担当する。

## フィールド

| フィールド | 内容 |
| --- | --- |
| repository | ユーザー情報へアクセスするRepository |
| cache | 取得済みユーザーを保持するキャッシュ |

## 関数

| 関数 | 責務 |
| --- | --- |
| GetUser | ユーザーIDからユーザー情報を取得する |
| UpdateUser | ユーザー情報を更新する |

## 関数の処理

### GetUser

#### 責務

ユーザーIDからユーザー情報を取得する。

#### 引数

| 名前 | 内容 |
| --- | --- |
| userId | 取得対象ユーザーのID |

#### 戻り値

| 名前 | 内容 |
| --- | --- |
| user | 取得したユーザー情報 |

#### 処理

1. userIdの形式を検証する
2. Repositoryからユーザー情報を取得する
3. API返却形式へ変換する
4. 呼び出し元へ返す
```

## 4. クラスセクション

クラス宣言前のコメントから、クラス自体の説明を生成します。

基本形:

```markdown
# クラス名

## 責務

内容

## フィールド

| フィールド | 内容 |
| --- | --- |
| fieldName | フィールドの説明 |
```

クラス宣言前の JSON-like Comment Out から、少なくとも次を取得します。

- Responsibility / 責務
- Fields / フィールド

Fields はクラスの説明書に正式に含めます。

Action / 処理など、その他のクラス情報をどこまで表示するかは今後決定します。

## 5. フィールド

クラス宣言前の JSON-like Comment Out に記述された Fields / フィールドを表として出力します。

例:

```text
フィールド: [
  repository: ユーザー情報へアクセスするRepository
  cache: 取得済みユーザーを保持するキャッシュ
]
```

生成結果:

```markdown
## フィールド

| フィールド | 内容 |
| --- | --- |
| repository | ユーザー情報へアクセスするRepository |
| cache | 取得済みユーザーを保持するキャッシュ |
```

実フィールド宣言とコメントの一致は検証しません。

## 6. 関数一覧

クラス内の関数 / メソッドについて、一覧を生成します。

基本形式:

```markdown
## 関数

| 関数 | 責務 |
| --- | --- |
| GetUser | ユーザー情報を取得する |
| UpdateUser | ユーザー情報を更新する |
```

関数名はソースコード上の宣言から取得し、責務はコメントから取得します。

## 7. 関数詳細

各関数 / メソッドについて、少なくとも次を出力します。

- 関数名
- 責務
- 引数
- 戻り値
- 関数内部のコメント

基本形:

```markdown
### GetUser

#### 責務

ユーザー情報を取得する。

#### 引数

| 名前 | 内容 |
| --- | --- |
| userId | 取得対象ユーザーのID |

#### 戻り値

| 名前 | 内容 |
| --- | --- |
| user | 取得したユーザー情報 |

#### 処理

1. 入力値を検証する
2. Repositoryからユーザーを取得する
3. API返却形式へ変換する
```

## 8. 関数内部コメント

関数 / メソッド内部の通常コメントを、**ソースコード上に現れる順番**で取得します。

例:

```ts
function getUser(userId) {
  // 入力値を検証する
  validateUserId(userId);

  // Repositoryからユーザーを取得する
  const user = repository.find(userId);

  // API返却形式へ変換する
  return toUserResponse(user);
}
```

生成結果:

```markdown
#### 処理

1. 入力値を検証する
2. Repositoryからユーザーを取得する
3. API返却形式へ変換する
```

### 原則

- コメントの出現順を維持する
- コメント本文を勝手に要約しない
- コメントから処理内容を推測して補完しない
- コメントのない処理をコードから推測して追加しない

## 9. JSON-like の Action

関数宣言前の JSON-like Comment Out に `Action` / `処理` が存在する場合、その情報も取得可能です。

ただし、

- 宣言前の Action
- 関数内部の通常コメント

は別の情報源です。

初期出力で両方を表示するか、内部コメントだけを「関数の処理」とするかは未確定です。

候補:

### 案A: 内部コメントのみ表示

```markdown
#### 処理
1. 関数内部コメント1
2. 関数内部コメント2
```

### 案B: 両方表示

```markdown
#### 処理概要
1. JSON-like Action 1
2. JSON-like Action 2

#### 実装コメント
1. 関数内部コメント1
2. 関数内部コメント2
```

Issue化前に決定します。

## 10. SemanticKeys

宣言前の JSON-like Comment Out の解析には SemanticKeys 設定を利用します。

責務表生成ツールと同様に、canonical key と alias は大文字小文字を区別せず解決します。

このツールが主に利用する Semantic Key:

- Responsibility
- Action
- Param
- Return
- Fields
- Note
- Error
- SideEffect

SemanticKeys 設定形式の共通化方法は、Tools全体の設計と合わせて今後整理します。

## 11. 通常コメントの扱い

通常コメントには SemanticKeys は適用しません。

例えば:

```ts
// キャッシュが存在しない場合のみDBへ問い合わせる
```

は、そのまま説明文として扱います。

コメント形式は各プログラミング言語の構文に従います。

## 12. 出力単位とディレクトリ構成

基本は**1クラス相当 = 1 Markdown** とします。

出力先フォルダをルートとして、入力プロジェクト内の**相対ディレクトリ構成を基本的にそのまま再現**します。

例:

入力:

```text
project/
├─ domain/
│  └─ user/
│     └─ UserService.cs
└─ application/
   └─ AuthService.cs
```

出力先を `docs-output/` とした場合:

```text
docs-output/
├─ domain/
│  └─ user/
│     └─ UserService.md
└─ application/
   └─ AuthService.md
```

### 仕様先行でも同じ

仕様を先にコメントとして書く場合も、既存実装のコメントから仕様書を生成する場合も、ディレクトリ生成ルールは変えません。

つまり、

```text
入力側の相対パス
        ↓
出力フォルダ配下へミラー
```

を基本とします。

これにより、ソースコードと生成された説明書の場所を対応付けやすくします。

### 複数クラスが同じソースファイルにある場合

同じソースファイル内に複数のクラス相当宣言がある場合は、同じ出力ディレクトリ内にクラス単位の Markdown を生成する方向とします。

例:

```text
src/models/User.cs
  ├─ User
  └─ UserProfile
```

↓

```text
output/src/models/
  ├─ User.md
  └─ UserProfile.md
```

Namespace / Package / Module を追加の分類階層として利用するか、全クラスを1ファイルへ集約するモードを残すかは未確定です。

## 13. GUI / CUI

GUI版・CUI版の両方を想定します。

GUIでは少なくとも:

- 対象プロジェクト / ディレクトリ
- 出力先
- 出力モード
- SemanticKeys 設定
- 生成

を扱います。

GUIは Alt 起点のキーボード操作に対応する方針です。

CUIは同じ解析・生成ロジックを利用します。

具体的なUI・コマンドは未確定です。

## 14. 言語対応

責務表生成ツールと同じ優先度を基本とします。

### 優先

1. Go
2. Python
3. C#

### 次点

4. Ruby
5. Rust
6. C++
7. Java

ただし「クラス説明書」という名称・出力構造は、Goのようにクラスを持たない言語では再検討が必要です。

Goでは struct / interface / package など、説明書の単位を別途定義します。

## 15. このツールの性格

このツールは、実態としては JSON-like 専用ツールというより**コメント解析・ドキュメント生成ツール**に近いものです。

JSON-like Comment Outs は、

- クラス責務
- クラスフィールド
- 関数責務
- 引数
- 戻り値

などの構造化情報を取得するために利用します。

通常コメントは、

- 実装中の処理単位
- 処理の理由
- 非自明な状態説明

など、実装内部の流れを取得するために利用します。

両方を組み合わせることで、ソースコードを読まずともコメントから概要を追える説明書を生成します。
