# Comment Validator / コメント検証ツール

**まだできてないよ...**
**Status: Planned — まだ実装されていません。**

JSON-like Comment Outs の不足や、コメントと実装の**機械的に確認できる不一致**を検出するツールです。

XML Documentation でよく行われる検証を参考にしつつ、JSON-like Comment Outs の思想に合わせて、**形式ではなく意味と宣言との対応**を確認します。

## やりたいこと

### コメント不足

- クラス / 関数 / メソッドにコメントがない
- 必要な Responsibility / 責務がない
- クラスで Fields / フィールドの説明がない
- 関数で Param / 引数の説明が不足している
- 戻り値があるのに Return / 戻り値の説明がない
- ジェネリック宣言に TypeParam / 型引数の説明がない

対象範囲を public のみにするか、private まで含めるかなどは設定可能にする方向です。

### 宣言名

推奨形:

```text
責務: [
  GetUser: ユーザー情報を取得する
]
```

について、

- コメントに書かれたクラス名と実装上のクラス名が違う
- コメントに書かれた関数名と実装上の関数名が違う

といった不一致を検出します。

### Param / 引数

XML Documentation の `param` と同様に、名前と網羅性を確認します。

- コメントに書かれた引数名が実装に存在しない
- 実装に存在する引数がコメントにない
- 引数名が変更されたのにコメントが古い
- 同じ引数名が重複して書かれている

### TypeParam / 型引数

ジェネリック型・関数について、

- コメントに書かれた型引数名が実装に存在しない
- 実装に存在する型引数がコメントにない
- 型引数名が変更されたのにコメントが古い

を検出します。

### Return / 戻り値

- 戻り値があるのに説明がない
- 戻り値がないのに内容付き Return がある
- 複数戻り値で、名前または順序の数が一致しない
- 名前付き戻り値の場合、コメント側の名前と一致しない

言語ごとの戻り値仕様に合わせて判定します。

### Fields / フィールド

- コメントに書かれたフィールド名が実装に存在しない
- 実装に存在する対象フィールドがコメントにない
- フィールド名変更後にコメントが古い
- 同じフィールド名が重複して書かれている

どのフィールドを必須対象にするかは言語・可視性設定に従います。

### Error / Exception

言語側で例外・エラー型を名前解決できる場合、

- コメントに記載された例外型・エラー型が存在するか

を検証できるようにします。

ただし、**その関数が本当にその例外を投げるか**までは検証しません。

### 参照

将来、関連クラスや参照先を表す Semantic Key を定義した場合は、XML Documentation の `cref` のように参照先の存在確認を行えるようにします。

### SemanticKeys 設定

- 同じ alias が複数の canonical key に登録されている
- canonical key と alias の解決が衝突している

など、設定上の曖昧さを検出します。

## Coverage

「ここコメントないよ！」を一覧化します。

例:

```text
Documentation Coverage

Class        18 / 20
Function    103 / 120
Field        44 / 51
Param       201 / 208
TypeParam     8 / 10
```

不足箇所も出します。

```text
Missing:
- UserService.DeleteUser
- OrderService.Cancel
- Cache<T>.T
```

Coverage の計算対象は設定可能にする方向です。

## 形式の違いは数えない

**形式・表記の違いは原則としてエラーに数えません。**

例えば、SemanticKeys で同じ意味に解決できるなら、

```text
責務
Responsibility
responsibility
```

は同じものとして扱います。

また、次の違いも原則として違反にしません。

- カンマの有無
- ダブルクォートの有無
- Key の記述順
- 空白やインデント
- 日本語キー / 英語キー
- SemanticKeys による alias
- ツールが正規化可能な表記差

JSON-like Comment Outs ではカンマを推奨しますが、**カンマがないこと自体は Validator の違反にしません。**

解析できないほど崩れている場合は、仕様違反として数えるのではなく「解析不能 / skipped」として別に報告する方向です。

## 検証しないこと

自然言語の意味や実装の正しさまでは検証しません。

- 責務の文章が本当に実装内容と一致するか
- Action の説明が実際の処理を正しく表現しているか
- 関数内部コメントが本当にその処理を説明しているか
- コメントの文章品質
- アルゴリズムが正しいか
- 仕様そのものが妥当か

このツールは、**名前・個数・存在有無・参照先など、機械的に比較できる範囲**を担当します。

## XML Documentation から参考にするもの

初期候補:

- コメント未記述の検出
- param の名前一致と網羅性
- typeparam の名前一致と網羅性
- returns の存在確認
- exception / error の参照先確認
- cref 相当の参照先確認

JSON-like 側では、XMLタグそのものではなく Semantic Key に正規化して扱います。
