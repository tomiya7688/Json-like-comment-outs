# JSON-like Comment Outs Specification

Status: **Draft v0.7**

> **この日本語版を仕様の正本 (canonical) とします。**

## 1. 目的

JSON-like Comment Outs は、XMLドキュメントコメントのような**宣言レベルの構造化コメントを、より書きやすく・読みやすい形式で表現すること**を目的とします。

特に次を重視します。

1. タグやマークアップより説明そのものへ集中できること
2. ソースコード上で責務・処理・入出力を素早く把握できること
3. コードを読むチームが理解しやすい言語で記述できること
4. 一定の構造を保ち、人間・AI・将来のツールが解釈しやすいこと
5. コメント規約そのものが大きな記述負担にならないこと

### 目的としないこと

- 有効な JSON として解釈できること
- XMLドキュメントコメントとの完全互換
- IDEや公式ドキュメント生成機能の完全な置き換え
- 英語の項目名を共通語として強制すること
- ソースコード中のすべてのコメントを JSON風にすること

## 2. 対象

JSON-like Comment Out は原則として次の宣言の直前に置きます。

- クラス
- 関数
- メソッド

関数・メソッド内部の処理説明、ローカル変数、条件分岐などは通常コメントで説明し、JSON-like 形式を要求しません。

## 3. ルールレベル

### 必須 (MUST)

JSON-like Comment Outs として基本的に満たすルールです。

### 推奨 (SHOULD)

合理的な理由がない限り採用することを推奨するルールです。

### 任意 (MAY)

必要な場合だけ利用するルール・項目です。

## 4. 言語

### 推奨

コメントは、**そのコードを読むチームが最も理解しやすい自然言語で書くこと**を推奨します。

説明文だけでなく、項目名もチームの言語に合わせて構いません。

日本語例:

```text
{
  責務:
  処理: []
  引数: []
  戻り値: []
}
```

英語例:

```text
{
  Responsibility:
  Action: []
  Param: []
  Return: []
}
```

## 5. Semantic Key

本仕様では、固定されたキー文字列ではなく、**キーが表す共通の意味**を定義します。

| 意味 | 日本語例 | 英語例 |
| --- | --- | --- |
| 対象の責務 | 責務 | Responsibility |
| 主な処理・振る舞い | 処理 | Action |
| クラスが保持する状態 | フィールド | Fields |
| 入力値 | 引数 | Param / Parameters |
| 戻り値 | 戻り値 | Return |
| 外部への状態変化 | 副作用 | SideEffect |
| 失敗条件 | エラー | Error |
| 補足情報 | 補足 | Note |

例えば `責務`、`Responsibility`、`役割` は、チーム内で「対象が担当するもの」という同じ意味として定義されていれば利用できます。

### 推奨

- チーム内で同じ意味のキーを一貫して使う
- 読み手が理解できる語彙を優先する
- 自動解析・Lint・ドキュメント生成を行う場合は、プロジェクト内でキー名を固定する

**構造は共有し、言語はチームに合わせる**ことを基本とします。

## 6. 基本構文

```text
{
  項目名: 値
  項目名: [
    名前: 説明
  ]
}
```

### 必須

- ブロックは `{` で始まり `}` で終える
- 項目名の後ろに `:` を置く
- 複数項目は改行して記述する
- リストは `[` と `]` で囲む

### 推奨

- 過度なネストを避ける
- 説明より記号が目立つ構造にしない
- 一つの項目へ複数の異なる責務を詰め込まない
- ソースコード上で流し読みしやすい整形を維持する
- 項目名と説明文はチームが読みやすい言語を使う

### 任意

- カンマ
- ダブルクォート

有効な JSON に変換できることは要件ではありません。

## 7. クラス

クラスでは、責務と保持する状態を特に重視します。

### 必須

- 責務に相当する項目
- フィールドに相当する項目
- 責務はクラスの担当範囲が分かる内容にする
- フィールドは主要フィールドの意味・役割・状態が分かる内容にする

### 推奨

- 処理・振る舞いに相当する項目
- クラスが提供する主要な振る舞いを書く
- 内部実装の細かい手順ではなく、クラス単位の振る舞いを書く

### 日本語例

```text
{
  責務: ユーザー認証の状態と認証処理を管理する
  フィールド: [
    token: 現在利用している認証トークン
    user: ログイン中のユーザー情報
  ]
  処理: [
    1: ログインする
    2: 認証状態を保持する
    3: ログアウト時に認証状態を破棄する
  ]
}
```

### 英語キー例

```text
{
  Responsibility: ユーザー認証の状態と認証処理を管理する
  Fields: [
    token: 現在利用している認証トークン
    user: ログイン中のユーザー情報
  ]
  Action: [
    1: ログインする
    2: 認証状態を保持する
    3: ログアウト時に認証状態を破棄する
  ]
}
```

## 8. 関数 / メソッド

### 必須

- 責務に相当する項目
- 処理に相当する項目
- 引数に相当する項目
- 戻り値に相当する項目
- 処理は原則として実際の処理順に並べる
- 処理は意味のある処理単位で記述する

### 推奨

- 処理番号は `1` から始めて連番にする
- 実装内部では意味のある処理単位に通常コメントを付ける
- 宣言前の処理一覧と実装内部の処理区切りがおおむね対応するようにする
- 非自明なローカル変数には通常コメントで意味を補足する

### 日本語例

```text
{
  責務: ユーザー情報を取得する
  処理: [
    1: userIdを検証する
    2: Repositoryからユーザーを取得する
    3: API返却形式へ変換する
  ]
  引数: [
    userId: 取得対象ユーザーのID
  ]
  戻り値: [
    user: API返却形式のユーザー情報
  ]
}
```

### 英語キー例

```text
{
  Responsibility: ユーザー情報を取得する
  Action: [
    1: userIdを検証する
    2: Repositoryからユーザーを取得する
    3: API返却形式へ変換する
  ]
  Param: [
    userId: 取得対象ユーザーのID
  ]
  Return: [
    user: API返却形式のユーザー情報
  ]
}
```

## 9. 任意項目

必要に応じて次の意味を持つ項目を追加できます。

### 副作用 / SideEffect

外部状態への変更を記述します。

### エラー / Error

呼び出し元が意識すべき重要な失敗条件を記述します。

### 補足 / Note

その他の重要な補足情報を記述します。

## 10. 実装内部のコメント

実装内部のコメントは JSON-like Comment Outs の構文対象外です。

### 処理単位

```ts
// キャッシュに存在しない場合のみRepositoryへ問い合わせる
if (!cachedUser) {
  user = repository.find(userId);
}
```

### 変数

```ts
// 税込み・割引適用後の最終請求額
const total = calculateTotal(order);
```

処理やコードをそのまま自然言語へ置き換えるのではなく、目的・理由・意味を優先します。

## 11. 保守

### 必須

- コメント内容を実装と一致させる
- 責務・処理・フィールド・入出力の意味が変わった場合はコメントも更新する

### 推奨

- コメントの形式を守ることより、読みやすさを優先する
- 読み手が理解できない言語のキーを慣例だけで使わない
- 任意項目を機械的に埋めない

## 12. Tooling

ツール固有の設定・挙動は、コア仕様ではなく各ツールの docs で定義します。

将来的には次のようなツールを実装できます。

- JSON-like Comment Out の検証
- XML Documentation への変換
- Markdown / HTML ドキュメント生成
- AI向けコードコンテキスト抽出

責務表生成ツールの設計は [tools/responsibility-table](../../tools/responsibility-table/README.md) を参照してください。
